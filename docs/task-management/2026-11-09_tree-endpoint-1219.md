# #1219: `/tree` fails on large boards, re-diagnosis

**Started:** 2026-11-09. **Status:** diagnosis done, no code change. Builds on
`2026-09-20_tree-endpoint-500-cloud-run-response-cap.md` (read it first; its "refuted" list still holds).
Worktree `/home/tracid/LingoLinq-AAC-offline`, branch `traci/fix/offline-boards-sync`.

## What was measured (local server, this branch, account aiden_parker)

`GET /api/v1/boards/aiden_parker/vocal-flair-84-with-keyboard/tree` (145 boards): 200, **98.8 MB**, 6.3 s.
`vocal-flair-112` (145 boards): 99.0 MB, 4.5 s. Breakdown of the first:

| Part | Size |
|---|---|
| `board.image_urls`, all boards | 97.2 MB (98.4%) |
| of which inline `data:image` pictures (2,902 entries) | ~95 MB |
| `board.buttons` | 1.4 MB |
| everything else | < 0.3 MB |

`image_urls` has 15,403 entries over 145 boards, 10,245 of them alternate-library keys (`<id>-<library>`).
With each inline picture replaced by a 200-byte link (the length of a production CDN link), the same tree is
**about 4.4 MB**; at `MAX_TREE` (500 boards, `boards_controller.rb:418`) about 15 MB. Estimate, not measured.

Server side, same request (`log/development.log`, request `efecbb5b`): `Completed 200 OK in 5525ms
(ActiveRecord: 3060.1ms (312 queries, 65 cached))`, **145** `start images_and_sounds lookup` lines (one per board).

## Diagnosis

1. **Response size (Cloud Run 32 MiB cap, mode 1): driven by inline `data:` pictures in `image_urls`.** Local
   boards carry them because the seed ran with uploads off (known; offline-boards task log, HANDOFF section 6).
   Production board JSON carries short CDN links (`lingolinq/quick-core-60`: 60 of 60 `image_urls` on
   `d34sa6lc5jfe66.cloudfront.net`, anonymous GET, 2026-11-09). So the cap is most likely hit only where boards
   hold inline pictures: local, and probably the dev/staging database (the September repro was on dev).
   NOT verified on dev, staging or production: `/tree` needs a signed-in token there (anonymous GET: 400
   "Access token required"), and this machine has no such account.
2. **Slowness (Rack::Timeout, mode 2): real on every environment.** `images_and_sounds_for` runs once per board,
   uncached: `lib/json_api/board.rb:243-244` calls it without the `as_lite` gate its neighbours have;
   `app/models/board.rb:2533` reads a cache that is never written (`set_cached` commented out at `:2561`).
   145 lookups, 312 queries, 5.5 s on an idle local server. Under concurrency it passes the 15 s Rack::Timeout and
   starves other requests on a one-instance service (dev, staging: maxScale 1 per the September log).
3. **Offline impact: indirect.** `/tree` is not part of the offline sync. Callers: Modern board page background
   warm (`routes/user/board-detail.js:160, 198`, `routes/user/board-alt.js:59`, via
   `board_detail_cache.warm_full_tree_if_root_only`), the guided tour (`components/guided-tour.js:955`). Its data goes
   to the in-memory cache and Ember store only (`utils/board_detail_cache.js:185-192`), never to the device. A failure
   makes Modern folder taps cold and feeds #1034's wrong "saved for offline" message; a slow `/tree` also takes server
   threads from sync requests.

## The issue's suggested fix 1 is unsafe as written

Gating `images_and_sounds_for` on `as_lite` and using `board.settings['image_urls']` instead would serve licensed
(protected) symbol links to users without the licence: the stored list is what the saving client sent
(`app/models/board.rb:2088`), and only the lookup swaps a protected image for its fallback when the viewer lacks the
source (`lib/json_api/image.rb:19-25`; the loop then writes that URL into `image_urls`, `json/board.rb:288`).
CONFIRMED by reading; not tested.

## Candidate fixes (not chosen; /fix-proposal applies)

- **A. One lookup for the whole tree:** collect the ButtonImage ids of root plus descendants, load them in one query,
  apply the same protected-source fallback per image, then serialize each board from that map. Keeps licensing
  behaviour; removes the per-board queries. Medium change in `#tree` and `JsonApi::Board`.
- **B. Cache per board, not per user:** the model's own TODO (`board.rb:2524-2530`): cache both protected and
  fallback URLs keyed on the board's update stamp, choose per viewer in process. Helps every endpoint, larger change,
  cache size was why it was turned off ("fills up half the cache").
- **C. Size:** only if real data can pass 32 MiB: stream or paginate descendants. Not needed if (1) holds.
- Regression guards either way: a query-count assertion on `#tree` for N boards, and a response-size assertion.

## Still to verify before a fix

1. One authenticated `/tree` on dev and on production for the largest tree an account has (bytes, time,
   `data:` count). Needs a dev account and a production test account.
2. Whether the dev/staging database's boards hold inline `data:` pictures (a read-only count over
   `boards.settings->'image_urls'`).

## Proposal (2026-11-11, Traci picking the item up on PR #1268; no code changed yet)

**Fact sheet.** (a) READ: `GET /api/v1/boards/:id/tree` is `boards_controller#tree` (`:419-459`), one buffered
`render json:` of root plus up to `MAX_TREE = 500` descendants (`:418`), lite serialization on unless the
`tree_lite_serialization` setting is 'false' (`:470-472`). Callers: the Modern board page's background warm after
a root-only paint (`routes/user/board-detail.js:156-177` through `board_detail_cache.warm_full_tree_if_root_only`,
`:476`), `routes/user/board-alt.js`, the guided tour; the offline sync does not use it. CONFIRMED. (b) SHAPES of the
failure: mode 1, the 32 MiB Cloud Run cap on an HTTP/1 response that is neither chunked nor compressed (no
`Rack::Deflater` anywhere in `config/`, CONFIRMED by grep), severed with no Ruby exception; mode 2,
`Rack::Timeout` at 15 s under concurrency, driven by `images_and_sounds_for` once per board with a cache that is
read but never written (`json/board.rb:244`, `board.rb:2533`, `:2561`): 145 lookups, 312 queries, 5.5 s locally.
CONFIRMED (measured 2026-11-09). (c) PAYLOAD: locally 98% is inline `data:` pictures in `image_urls` (a seed
artifact); production boards carry CDN links (`quick-core-60`, anonymous read 2026-11-09), estimate 4.4 MB per 145
boards and about 15 MB at 500. The alternate-library keys (`<id>-<library>`, two thirds of the entries) are read by
the client (`utils/button.js:631`), so they cannot simply be dropped. NOT VERIFIED: the size of the largest real
tree on staging or production (needs a signed-in token).

**Candidates.**
- **A. One image lookup for the whole tree (server; the slowness, which is real on every environment).** In
  `#tree` and `#bulk`, collect the ButtonImage ids of root and descendants, load them once
  (`ButtonImage.find_all_by_global_id`), run `cached_copy_urls` and `JsonApi::Image.as_json` once per image with
  the same viewer arguments as today, and hand each board its images through an additive
  `args[:images_by_id]` that `images_and_sounds_for` uses instead of querying. Licensing behaviour unchanged (same
  `JsonApi::Image` path, same protected-source fallback). Image queries become O(1) in boards; the per-board
  sounds check stays (it only queries for boards with sound buttons). Test: the spec file's `count_board_sql`
  harness; the image-query count for a tree of 3 image boards equals that for 6. Mutation: drop the preload.
- **B. A byte budget with paging (server plus client; the cap).** `#tree` serializes descendants in order until
  the JSON passes a budget (8 MiB; constant, overridable for the spec) and then stops and returns `next_offset`;
  `?offset=` resumes. `warm_full_tree_if_root_only` loops until there is no `next_offset`, sharing one in-flight
  entry, and reports the total descendant count. A budget rather than a fixed page size is robust to data shape
  (inline pictures, huge boards). An app build without the loop gets the first page only: a partial warm, which
  is what `MAX_TREE` already gives today, never an error. `root_only` requests unchanged. Tests: a tree whose
  budget is forced small returns `next_offset` and the second request completes the set with the permission
  filter still applied per page; a frontend test that the loop ingests every page. Mutation: ignore `next_offset`.
- **C. Response compression (`Rack::Deflater`).** 5 to 10x on link JSON, little on inline pictures; shared
  config with a blast radius on every response and CPU on one-instance services: a separate infra proposal for
  Scot, not this PR.
- **D. Client only: warm through the existing paged `/bulk` BFS (`prefetch_all`, `MAX_BULK = 200`).** No server
  change for size, but a 200-board layer can still pass the cap on inline-picture data, and `/bulk` has the same
  per-board image cost, so the slowness stays. Not sufficient alone.
- **E. Streaming (chunked) to lift the cap.** Changes the response mechanics of one endpoint under Puma and
  `Rack::Timeout`, hard to test, and does nothing for the slowness. Rejected.
- Rejected, as in the 2026-11-09 section: the issue's "gate `images_and_sounds_for` on `as_lite`" serves licensed
  symbol links to viewers without the licence.

**Recommendation: A, then B, each as its own unit with its own red test and review; C handed to Scot.** A fixes
the mode that is confirmed everywhere and shortens every `/tree` and `/bulk`; B makes the cap unreachable
whatever the data holds. If time is short, A alone is a complete, shippable unit, and B can follow in its own PR.
Risks: A touches `JsonApi::Board.as_json`'s image plumbing, used by every board response, so the new argument is
additive and the default path is untouched; B adds a loop to the Modern warm and a parameter to the endpoint, and
old app builds degrade to today's partial warm. Both need the dual review (server change on a permission-filtered
list). Estimate: A half a day with review; B half a day to a day. Open question: one authenticated `/tree` on
staging for the largest tree there (bytes and seconds) would say whether production is near the cap today; it
needs the staging account, and B is worth building either way because the cap fails hard.

### Unit A: one image lookup for the whole tree (2026-11-11, Traci: proceed with A, B, B2 on #1268)

**Facts.** (a) READ: `Board#images_and_sounds_for(user)` (`app/models/board.rb:2523-2566`) runs once per board
from `JsonApi::Board.as_json` (`lib/json_api/board.rb:244`, no `as_lite` gate), and does, per board:
`known_button_images` (`:2570-2579`: `ButtonImage.find_all_by_global_id(image_ids)`, which is a `User.where`
for sub-ids plus the `where(id:)`, so about 2 queries per image-bearing board; matches the 312 queries over 145
boards measured 2026-11-09), `user.enabled_protected_sources(true)` (cached, `user.rb:4485`),
`ButtonImage.cached_copy_urls(bis, user, nil, protected_sources)` (`app/models/concerns/uploadable.rb:719-791`:
in memory, except a `ButtonImage.where(url:)` for protected lessonpix links with no cached copy and a
`record.save` when one is found), `JsonApi::Image.as_json` per image (reads the record's own settings), and
`known_button_sounds` only when a button has a sound. `get_cached` is read per board and never written (`:2561`).
`grid_buttons` reads board content (`BoardContent.load_content`, cached per request for offloaded content). (b)
SHAPES: `#tree` serializes root plus up to 500 permission-filtered descendants, `#bulk` up to 200; both lite by
default; the full (non-lite) path also runs `ButtonImage.find_by_global_id` per image (`json/board.rb:271`),
unchanged here. (c) CROSS-FILE: the existing spec pins lite's per-descendant cost as "a small bounded constant"
(`spec/controllers/api/boards_controller_spec.rb:3841-3870`) and that `ButtonImage.find_by_global_id` is not
called; neither pins the count per board exactly, so A tightens, not rewrites, them.

**Proposal A.** `Board.preload_button_images(boards, user)`: the union of `image_id`s over the boards'
`grid_buttons`, one `ButtonImage.find_all_by_global_id`, one `cached_copy_urls` over all of them, then each board
gets its own images in its own button order through `button_images_preloaded(by_id)` (sets `@button_images`
and a flag). `images_and_sounds_for` keeps its code path and arguments; with the flag set it skips its own
`cached_copy_urls` (already done for the set). `#tree` calls the preload for `[root] + descendants` after the
permission filter, `#bulk` for the visible boards. The licensing path is untouched: the same `JsonApi::Image.as_json`
arguments decide protected versus fallback per viewer. Alternative rejected: writing the per-user cache back on
(`set_cached`, turned off for cache size; a request-scoped batch needs no cache). Risk: a board whose grid
changed between preload and serialization (none: same request, same objects); a preload for boards with no
images (no ids, no query). Tests: `#tree` and `#bulk` issue the same number of `button_images` queries for 3
image boards as for 18 (today it grows by about 2 per board); the existing bounded-constant and no-`find_by_global_id`
examples stay. Mutation: skip the preload call in the controller (the count grows again).

**Review of the A proposal (2026-11-11): build with changes, applied.** High, confirmed at
`app/models/concerns/global_id.rb:143`: `find_all_by_global_id` keeps a record by the FIRST requested id with that
database id, so a lookup over the union of many boards' ids lets one board's stale nonce drop another board's
valid image, and a dropped image falls back to the stored `image_urls` entry; built instead as one
`ButtonImage.where(id:)` indexed by id with find_all's nonce rule applied per board to that board's own ids.
Medium: `find_all_by_global_id` is quadratic in the id count (1.25 s of CPU at 5,158 ids, measured by the
reviewer); the hash-indexed lookup avoids it. Medium: the red specs counted queries only; added: each board's
`image_urls` names exactly its own buttons' images (tree and bulk), the nonce rule per board, a protected image
shared by two boards serialized identically with and without the preload for a licensed and an unlicensed viewer,
`find_all_by_global_id` never called, the `users` query count constant. Low: the preload runs under the
`tree_lite_serialization` switch so 'false' restores the whole pre-fix path; the batched flag is cleared where
`@button_images` is cleared (`generate_stats`, `reload`); the bulk spec posts. Mutations: no preload (both
one-lookup examples red); no per-board nonce rule (the nonce example red). Observation, not changed: for a viewer
without the licence, the `<id>-original` alternate in `image_urls` carries the untokenized protected URL (built from
`best_url`, `lib/json_api/image.rb:62-70`), with or without the preload; the `protected_image` endpoint decides
what that URL serves, so it is noted for the licensing pass rather than treated as a leak here.

### Units B and B2: a byte-budgeted page on `/tree`, and a client that warms a bounded number of pages

**Facts.** (a) READ: `#tree` takes `root.settings['downstream_board_ids'].first(MAX_TREE)`, loads them all
(`find_all_by_global_id`), permission-filters, serializes all, renders once (`boards_controller.rb:432-459`).
The only full-tree client call is `board_detail_cache.warm_full_tree_if_root_only` (`:462-497`), used by the Modern
route on a cache hit and after a root-only paint (`routes/user/board-detail.js:160, 198`) and by the Basic route
(`routes/user/board-alt.js:59`); callers read `result.warmed` and `result.descendant_count` only (diag marks). It
ingests with `root_only: false`, which clears the root-only mark (`ingest_tree`, `:393-418`), so a warm is
all-or-nothing per request today. `root_only=1` requests (the prefetch) are separate and unchanged. (b) SHAPES:
Cloud Run severs an HTTP/1 response over 32 MiB that is not chunked or compressed; the app sends neither. A board's
JSON is a few KB to tens of KB on production (links) and up to ~700 KB locally (inline pictures). (c) CROSS-FILE:
old app builds send no `offset` and read no `next_offset`; the cache dedupes by key and id (`_index`), so a board
seen on two pages is one entry.

**Proposal B (server).** `?offset=` indexes the capped id list. A page loads at most `TREE_PAGE_IDS = 100` ids
(one `find_all_by_global_id`), permission-filters them, preloads their images (unit A), and serializes in order,
stopping once the accumulated JSON passes `TREE_PAGE_BYTES = 1 MiB` (the page always holds at least one board). When
ids remain (filtered-out ids count as consumed), the response carries `next_offset`. `MAX_TREE` stays the overall
cap; `root_only` is unchanged. A board over the budget by itself is its own page, so the only way past 32 MiB is one
board that large. Tests: with the budget forced to 1 byte, each page holds one board and `next_offset` walks the
whole set in order; with `TREE_PAGE_IDS` forced to 2, pages of two; a board the viewer may not see is skipped and
the offsets still cover every visible board exactly once; a `root_only` request carries no `next_offset`; the
response of the largest fixture tree stays under budget plus one board. Mutation: never set `next_offset`.

**Proposal B2 (client).** `warm_full_tree_if_root_only` fetches `/tree`, then `/tree?offset=n` while the answer
carries `next_offset`, up to `TREE_WARM_MAX_PAGES` (4; 2 when `capabilities.installed_app`): descendants of every
page go to the cache and the store as they arrive; the root-only mark is cleared when the loop ends (the last page,
or the cap), so an interrupted warm leaves the mark and the next open warms again, while a capped warm counts as
done and deeper folders load on their first tap as they do today when a warm has not reached them. The result keeps
its shape: `{warmed, descendant_count}` over all pages, plus `partial: true` when capped. One in-flight entry per
key for the whole loop. Tests: two pages are both ingested and counted, with two requests; the cap stops after N
pages with `partial`; a failed later page leaves the mark set; an answer without `next_offset` (an old server) ends
after one request as today. Mutations: ignore `next_offset`; ignore the cap.

Alternatives rejected: a fixed page size alone (a page of inline-picture boards can still pass the cap); streaming
(see section above); warming the whole tree regardless of device (the memory the item exists to bound).

**Review of the B and B2 proposal (2026-11-11): build with changes, applied.** High, confirmed at
`global_id.rb:140`: `find_all_by_global_id` answers in database order, so a page that followed it with a positional
`next_offset` would skip boards; a page walks the id slice in its own order through a by-id lookup, and the spec
reverses the list so database order and list order differ. Medium: `ingest_tree` clears the root-only mark on any
call without `root_only`; the loop ingests the root with the mark kept at offset 0, descendants page by page, and
clears the mark itself when the loop ends. Medium: a page that always fails would re-warm every open; the entry
keeps a resume offset and a failure count, the next open resumes there, and a second failure ends the warm as
partial. Medium: old app builds would have had less coverage than today (1 MiB against 145 boards that fit); the
server pages only when `offset` is sent (new builds send 0) and answers a request without it in one response
stopped at 24 MiB, never less than before and never near the cap. Medium: cost; each board is encoded once and the
body assembled from the pieces, and a page loads and image-preloads 25 boards at a time so a budget-stopped page
does not load 100. Low: `offset` clamped to 0..MAX_TREE (a 20-digit value raised before). Low: the small page cap
keys on `capabilities.mobile` (the iPad detection of #1201), not `installed_app`. Built: `TREE_PAGE_IDS = 100`,
`TREE_PAGE_CHUNK = 25`, `TREE_PAGE_BYTES = 1 MiB`, `TREE_LEGACY_BYTES = 24 MiB`, `next_offset` counting every id
walked (a denied board counts; an all-denied page still advances); client `TREE_WARM_MAX_PAGES = 4`,
`TREE_WARM_MAX_PAGES_MOBILE = 2`, `TREE_WARM_MAX_FAILURES = 2`. Specs: list order with a reversed list, page size,
denied board before the budget trips, all-denied page, legacy request, clamp, root_only never pages, the 18-board
fixture under budget; client: the walk with each request carrying the previous `next_offset`, old server, a
non-advancing `next_offset`, the cap on web and mobile, failure then resume then partial. Mutations: server, no
`next_offset` (4 red) and database order (1 red); client, ignore `next_offset`, no cap, no resume. The 4th
`ember/no-runloop` baseline row of `board_detail_cache.js` (936) is held by placing the loop's explanation in the
rewritten region.
