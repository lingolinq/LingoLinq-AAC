# Migrate Job ran on the static cache token (GitHub #423)

**Found** while reviewing #1168. `RedisInit.resolved_cache_token` (`config/initializers/resque.rb`) returns `CACHE_TOKEN`, else `K_REVISION`, else `'abc'`, and `RedisInit.init` reads it at every Rails boot. In `.github/workflows/deploy-cloudrun.yml` the migrate Job was deployed with `--set-secrets "$BOOT_SECRETS"` only, `CACHE_TOKEN` sat in `NON_BOOT_SECRETS`, and Cloud Run Jobs get no `K_REVISION`. So every deploy's migration and every one-off `rails runner` or console through the Job used `'abc'`.

**Change.** `CACHE_TOKEN` moved from `NON_BOOT_SECRETS` to `BOOT_SECRETS`. Every other consumer (the existence check, web, the worker pool, the scheduler and its readback, `assert-runtime-secrets`) takes the union of both sets, so only the migrate Job gains a secret. Both run as `$RUNTIME_SA`, which already reads `CACHE_TOKEN`. Hand recipes that copy `$BOOT_SECRETS` (for example `scripts/gcp/PHASE5-CLEAN-DB-REHEARSAL.md`) now pick it up too.

**Red/green.** `spec/config/deploy_cloudrun_secrets_spec.rb` failed on `develop` ("puts CACHE_TOKEN in the boot set": expected 1, got 0) and passes after the move; with `spec/initializers/resque_redis_options_spec.rb`, 27 examples, 0 failures at the time; 34 after the fail-closed examples below. `scripts/ai-endpoint-guard.sh` still passes.

**Fail closed (#423's second option).** `resolved_cache_token` now raises when it runs on Cloud Run (`K_SERVICE`, `CLOUD_RUN_JOB` or `CLOUD_RUN_WORKER_POOL` present, the variables Cloud Run itself injects for a service, a Job and a worker pool) and `CACHE_TOKEN` is blank. That turns a web revision that lost `CACHE_TOKEN`, which used to fall back silently to its own `K_REVISION`, into a boot failure. It keys on Cloud Run, not `Rails.env.production?`, because the Docker build runs `assets:precompile` in production mode with no `CACHE_TOKEN`; local development, the test suite, CI and the Docker image build are unchanged (the deployed dev environment does get the change). Red/green: the six new `on Cloud Run` examples in `spec/initializers/resque_redis_options_spec.rb`; five failed before the guard. Mutants: no guard fails 5, and the guard moved after the `K_REVISION` tier fails 3 (it lets the real service shape, `K_SERVICE` plus `K_REVISION`, through).

**Why this is safe to ship without a live check first.** A blank `CACHE_TOKEN` value (a whitespace-only version passes the existence check) would make the next deploy's migrate Job refuse to boot before web or the worker change, so the deploy is blocked. Between deploys the same version would be picked up wherever a process starts, because Cloud Run reads `:latest` at instance start: new web instances, a restarted worker and each hourly scheduler run would refuse to boot. Before this change it split the cache silently instead. Recovery is to re-add the previous version's exact value (`gcloud secrets versions access PREVIOUS_VERSION --secret CACHE_TOKEN --project lingolinq-prod | gcloud secrets versions add CACHE_TOKEN --project lingolinq-prod --data-file=-`, with PREVIOUS_VERSION the version number before the bad one; use `lingolinq-nonprod` for nonprod, whose version numbers are separate), so running and new processes agree; a different value would leave already-running web and worker processes on the old token and new ones on the new token, the same split, and needs every surface restarted or redeployed. A hand-made Cloud Run Job that boots Rails without `CACHE_TOKEN` (`lingolinq-admin-audit` in prod, if still used; `lingolinq-identify-check` runs `identify -version` and never boots Rails) would fail at boot the next time its image is updated, loudly; `gcloud run jobs update lingolinq-admin-audit --project lingolinq-prod --region us-central1 --update-secrets CACHE_TOKEN=CACHE_TOKEN:latest` fixes that.

Separate and unverified: the migrate Job gets no `APP_ENV_VARS`, so it has no `REDIS_NAMESPACE_SUFFIX`. If nonprod web and the worker use `-dev` (`docs/INFRASTRUCTURE.md`), the nonprod migrate Job's cache and Resque keys use the unsuffixed namespaces instead. That predates this change; the live variable value was not checked.
