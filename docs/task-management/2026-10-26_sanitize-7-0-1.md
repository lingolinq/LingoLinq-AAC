# sanitize 7.0.1 (GHSA-wgw9-qhqg-8hv5)

Issue #1216. Branch `traci/security/sanitize-7-0-1`.

## Problem

`security-scan`'s `bundle-audit check --update` began failing on every PR when GHSA-wgw9-qhqg-8hv5 reached
the advisory database: `sanitize` 7.0.0, fixed in 7.0.1.

## Exposure (verified)

- **The vulnerable call:** `Processable#process_html` (`app/models/concerns/processable.rb:126-128`) runs
  `Sanitize.fragment(html, Sanitize::Config::RELAXED)`. RELAXED allows `<style>`, `@media`, about 750
  properties (including `position`), and only `http`, `https` and relative URLs.
- **Callers:**
  - `UserGoal` `description` (`app/models/user_goal.rb:431`) and `sequence_description` (`:459`);
  - `UserIntegration` `description` (`app/models/user_integration.rb:165`).
- **What 7.0.0 let through:** a nested rule
  (`p{color:not(z), *{...url(data:...)}}`) or a nested `@media` (`p{@media all{...url(data:...);a{}}}`)
  kept a `data:` URL that the flat form strips. No script execution: the advisory rates it Moderate,
  CVSS 5.3.
- **`process_string`** (the default config, which allows no `<style>`) is not affected.

## Change

- **The bump:** `bundle update --conservative sanitize`, 7.0.0 to 7.0.1. Its `crass` requirement
  tightened to `~> 1.0.8`, which the Gemfile already requires.
- **The floor:** `gem 'sanitize', '>= 7.0.1'` with the advisory named in a comment, matching the `crass`
  and `rails-html-sanitizer` pins.
- **New spec:** `processable_spec.rb` "should not let nested CSS carry a blocked url() or property past
  the sanitizer". It covers a `data:` and a `javascript:` URL and the disallowed `inset` property, with
  positive controls that `<style>` survived and that the flat form is stripped. Each payload leaks on 7.0.0.
- **Existing spec `processable_spec.rb:52`:** its style-attribute half was rewritten, with Traci's Rule 14
  approval on 2026-10-26. 7.0.1 removes any declaration holding a bad `url()` inside `(...)` (changelog,
  4th security bullet), so the old control `include('style="color:')` encoded 7.0.0 behaviour. The new
  control is a declaration after the bad one (`font-weight: bold`). It keeps
  `not_to include('javascript:')` and adds `not_to include('color:')`. An adversarial review ran on the
  proposal before the edit. The revised assertions fail on sanitize 7.0.0 with crass 1.0.6, 1.0.7 and
  1.0.8, and on `Sanitize::Config::BASIC`. Forcing sanitize 7.0.1 onto crass 1.0.6 or 1.0.7 (bypassing
  gem activation) passes them, because 7.0.1's own bad-url removal hides the crass bug for this input. So
  on 7.0.1 the test no longer detects a crass regression by itself. That combination cannot be installed:
  sanitize 7.0.1 requires `crass ~> 1.0.8` and the Gemfile floors `crass >= 1.0.8`.

## Regression check

- **Same output on normal content:** 7.0.0 and 7.0.1 give identical results for ordinary style
  attributes, `https` background images, a valid `@media` block, links, lists and tables. Only malformed
  or nested CSS changes.
- **Full RSpec:** 8,271 examples, 4 failures, 51 pending. The 4 failures are
  `boards_controller_spec.rb:26`, `:63` and `:89`, and `throttling_spec.rb:87`. They fail identically on
  clean `develop`, and all 4 pass on 7.0.1 after `bundle exec rails extras:assert_js` (the task CI runs
  before RSpec). The cause is the fresh worktree, which has none of that task's gitignored outputs.

## Accepted risk (not fixed)

- **Plain `<style>` in descriptions is still allowed (verified on 7.0.1).** RELAXED keeps `<style>`, and goal
  and integration descriptions render as live HTML (`templateHelpers.safe` returns `htmlSafe`). The CSP is
  report-only. So someone can still restyle the page with flat CSS, without needing the advisory's bypass:
  - **No script runs and no account data is reachable.** The worst case is a full-page overlay or an
    `https` beacon that reveals a viewer's IP.
  - **It cannot happen by accident.** Descriptions are entered in a plain `<textarea>`, so a Word or
    Google Docs paste arrives as plain text.
  - **Only a trusted insider could do it**: the communicator, a supervisor with `edit`, a unit manager or
    an org admin. They can already do worse directly.

  Traci decided on 2026-10-27 not to fix this or open an issue; the same reasoning covers descriptions
  stored before the bump.
