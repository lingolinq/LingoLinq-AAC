<objective>
Give the Ember `lesson` route a graceful expired-link experience for the client-side SPA transition path (when an already-booted app navigates to `/lessons/:lesson_id/:lesson_code/:user_token` with an expired or otherwise unresolvable share token). Today `routes/lesson.js` has ZERO error handling: `model()` is a bare `findRecord` and the route has no `error` action. When the token is expired, the backend `api/lessons#show` returns HTTP 200 but the serializer skips the `extra_user` block, so `json['id']` comes back as the bare `lesson.global_id` — NOT the composite id Ember requested. This is a guaranteed Ember-Data id mismatch; its runtime effect (reject vs resolve-a-mismatched-record) MUST be verified at runtime, and the implementation must handle whichever it is.

Purpose: This is the client-side half of the expired-link UX. Plan 01 handles the fresh-navigation (emailed link) half in Rails; when Plan 01 boots the Ember shell for an expired link, Ember's lesson route runs the same code path this plan hardens, so both entry paths converge on ONE explanatory experience.

Output: A hardened `routes/lesson.js` + `controllers/lesson.js` flag, a conditional link-expired panel in `lesson.hbs` with i18n copy, extracted `en.json` strings, and an acceptance test plus a documented runtime verification of the Ember-Data findRecord behavior on an expired token.
</objective>

Backend behavior on an EXPIRED token (lib/json_api/lesson.rb + api/lessons_controller#show, origin/staging):
- `#show` calls `User.find_by_lesson_share_token(user_token)` -> nil for an expired token, then renders 200 with `extra_user: nil, extra_user_token: user_token`.
- The serializer only sets the composite id and the `user` block inside `if args[:extra_user]`. With extra_user nil, that block is SKIPPED, so `json['id']` stays the DEFAULT `lesson.global_id` (bare) and there is NO `user` in the payload.
- Therefore, for an expired token, findRecord('lesson', 'GID:code:token') receives a payload whose id is 'GID' (mismatch) and which has no `user`. For a VALID token, the payload id equals the requested composite and includes `user`.
- The reliable client-side signal for "token unresolved" is: findRecord rejected, OR it resolved but the returned record has no `user`. Handle BOTH.

i18n import pattern in routes (origin/staging): `import i18n from '../utils/i18n';` (see routes/board.js, routes/application.js). Template helper pattern: `{{t "Finished Lesson" key="finished_lesson"}}` (see current lesson.hbs).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| booted SPA -> api/lessons#show | Ember Data findRecord crosses here with a user-supplied composite id containing the share token. The JSON endpoint is deliberately tolerant (200 with extra_user nil) for an unresolved token. |
| rendered client -> lesson iframe | The lesson template embeds third-party lesson content in an iframe (`this.model.url`); rendering it for an unresolved/sentinel record could load an unintended URL. |
