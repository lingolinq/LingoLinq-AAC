<objective>
Make `boards_controller#lesson` (the Rails-rendered HTML shell that boots Ember on a fresh browser navigation — e.g. clicking an emailed lesson link) stop returning a bare `/404` when a lesson's `lesson_share_token` has expired. When the lesson exists (and its nonce matches) but the share token no longer resolves to a user, boot the Ember app anyway so the frontend (Plan 02) can render an explanatory "this link is no longer valid" experience. Keep `/404` only for a genuinely missing or nonce-mismatched lesson.

Purpose: An expired emailed lesson link currently dead-ends at a bare 404 with no explanation and no recovery path. This is the fresh-navigation half of the expired-link UX (the client-side SPA transition half is Plan 02). This plan changes ONLY what the controller does after `User.find_by_lesson_share_token` returns nil — it does not touch the token's crypto, minting, the feature flag, or the finder's accept-side behavior (all LOCKED).

Output: A modified `boards_controller#lesson`, plus a new `describe "lesson"` block in the controller spec that proves the three outcomes (expired -> render index, missing -> 404, valid -> render index) including a runtime-shape assertion using a genuinely-expired token string.
</objective>

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-01-01 | Information disclosure | boards#lesson now renders the shell (not 404) when the lesson exists but the token is bad, vs 404 when the lesson is missing — a lesson-existence oracle | accept | Reaching the render-shell branch requires `@lesson.nonce == params['lesson_code']`, i.e. the caller must already present the lesson's secret nonce. An attacker who does not know the nonce gets `/404` regardless (guard unchanged). The oracle is therefore gated behind knowledge the caller already has; no new capability is exposed. Verified by the nonce-mismatch->/404 spec example. |
| T-01-02 | Information disclosure | expired vs malformed vs wrong-sig token distinction (token-validity oracle) | mitigate | `find_by_lesson_share_token` returns nil with no reason for every failure mode; the controller takes ONE render path for all of them (no branching on failure reason). Proven by the expired-token and malformed-token examples both asserting `render_template(:index)` + not-redirect (UX-05). |
| T-01-03 | Spoofing / elevation | rendering the shell for an unresolved token could be mistaken for granting lesson access | accept | Rendering `:index` only boots the SPA HTML directly; it grants no USER-scoped data. `#complete` still requires a valid user via `exists?` — unchanged by this plan. No completion can be recorded for an unresolved token. **Corrected 2026-07-11 (Codex review, High):** this entry originally also claimed "[boots the shell]... grants no data" as if that covered LESSON CONTENT too — that was wrong. Booting the shell causes the SPA to immediately call `findRecord` -> `api/lessons#show`, which DOES return full lesson content (title/url/description) regardless of token validity, independent of this controller. See T-01-05 for the actual disclosure this created and its fix. |
| T-01-04 | Information disclosure (timing) | (adversary-review finding) expired (fast, no DB) vs malformed/legacy (DB round-trip) vs valid (DB round-trip) tokens now differ only by response latency, since all three return 200 post-fix | accept | Requires the secret nonce to reach this branch at all; the information gained (whether one's OWN token is expired vs malformed) has near-zero attacker value, and this is weaker than the pre-existing 200-vs-404 oracle it replaces. No code change; documented residual. |
| T-01-05 | Information disclosure | (Codex review finding, High) booting the shell unconditionally makes the browser auto-fetch full lesson content (title/url/description) via `findRecord` -> `api/lessons#show` regardless of token validity — the new "links stop working" copy did not match this reality | mitigate | `app/views/boards/index.html.erb` now embeds `window.lesson_share_token_valid` (from this same `@user`/`find_by_lesson_share_token` result) so `routes/lesson.js` can skip `findRecord` entirely when the token didn't resolve — no content-fetching API call happens for this entry point.
